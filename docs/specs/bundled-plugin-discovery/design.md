# 发行包内插件自动发现 — 设计

**Spec**: `bundled-plugin-discovery`
**依据**: 用户已批准的 `requirements.md`（2026-10-22）
**状态**: 已实现并完成本功能验收（2026-10-22）；实际验证证据与范围见 `tasks.md`

## 1. 设计范围与现状

本设计只解决发行包内插件的自动发现，不改变插件协议、不引入多根叠加，不混入前次安全审计的修复。

现有发行包布局已经满足需求，无需调整归档内容：

```text
<解压目录>/
  netutils[.exe]
  plugins/
    <plugin>/
      bin/<binary>[.exe]
```

依据为 `README.md:67-78`、`.github/workflows/release.yml:212-215` 和 `:242-244`。插件清单仍从 workspace metadata 推导，不改成手写清单。

现有根目录入口是 `src/plugin.rs:1173-1183` 的 `plugin_base_dir()`，各消费者已共享该入口：

| 行为 | 现有调用点 |
|---|---|
| 拼装插件目录与二进制位置 | `src/plugin.rs:1186-1188`、`:1163-1170` |
| 安装、安装后二进制检查及写锁 | `src/plugin.rs:194-205`、`:234-250` |
| 更新 | `src/plugin.rs:428-440`，复用安装逻辑 |
| 列举与目录显示 | `src/plugin.rs:347-375`、`:478-485` |
| 删除及其路径安全校验 | `src/plugin.rs:444-474`、`:1027-1040` |
| 锁文件路径、读写 | `src/plugin.rs:1043-1059` |
| 执行当前根中的插件，然后回退 PATH | `src/plugin.rs:755-777` |

因此只需更换统一的目录选择策略，保留上述调用链；不为每个命令分别实现发现逻辑。

## 2. 根目录选择与生命周期

### 2.1 选择顺序

首次需要插件根时，按以下顺序决定：

1. 若 `NETUTILS_PLUGIN_DIR` 为 `Some`，直接使用原始值。
2. 否则取得正在运行的主程序位置，只检查其同级 `plugins/`；该路径为目录时选中。
3. 否则沿用 `USERPROFILE/.netutils/plugins`、`HOME/.netutils/plugins`、相对 `.netutils/plugins` 的既有顺序。

相关边界：

- 使用 `var_os` 和路径类型，不将环境变量先转成 UTF-8 字符串。
- 显式空值、相对路径、不存在路径与非 Unicode 值保留原有语义；不增加 trim、存在性过滤或 canonicalize。
- 包内候选用 `is_dir` 判断：空目录有效；同名普通文件、断开的链接及无法读取元数据的候选不算已发现的目录。
- 可读、可遍历、可执行但不可写的目录仍可选中，不通过写入探针判断资格。
- 取得主程序位置失败或没有父目录时，回到原默认链，不 panic，也不猜测工作目录。
- 不检查候选目录是否拥有某个插件或锁文件，不因缺少一个插件改选用户目录。
- 不扫描工作目录、任意祖先目录或 PATH 来推断发行包位置，不新增 `../plugins` 候选。

### 2.2 每次 CLI 调用固定一个根

新策略包含文件系统目录判断，不能在每个消费者调用时重新选择根。安装在启动 cargo 前计算根（`src/plugin.rs:194`），安装后又查询二进制、写锁（`:234-250`）；列举和删除安全校验也会多次调用根入口。若包内候选在这段时间出现、消失或变得不可读取，重复判断可能令同一命令的不同阶段使用不同根。

生产入口使用标准库 `OnceLock<PathBuf>`，在首次插件目录访问时初始化，后续返回该路径的副本。下一次启动 CLI 时重新选择，不写磁盘缓存，不在普通核心命令启动时预先探测插件。

这里固定的是进程内路径值，不是文件系统对象身份；不保证目录不会被替换、符号链接目标不会变化，也不提供跨进程事务或 TOCTOU 防护。保留原删除安全检查，不把缓存当作其替代品。

## 3. 模块与接口

### 3.1 插件私有路径模块

新增 `src/plugin/paths.rs`，由 `src/plugin.rs` 声明私有子模块并导入同名 `plugin_base_dir`。不改 `main.rs`，不把该接口公开到 crate 外。

设计接口如下；这里只规定签名，不提供本阶段实现：

```rust
pub(super) fn plugin_base_dir() -> PathBuf;

fn select_plugin_base_dir(
    explicit_dir: Option<&OsStr>,
    executable: Option<&Path>,
    user_profile: Option<&OsStr>,
    home: Option<&OsStr>,
    is_dir: impl FnOnce(&Path) -> bool,
) -> PathBuf;
```

- 生产入口负责读取环境、主程序位置和真实目录元数据，并保存进程内选中的根。
- 私有选择器只根据传入数据返回路径，不读取全局环境、不改变工作目录、不写文件。
- 选择器自行构造 `executable.parent()/plugins`，测试不能只传入预计算的包内目录而漏掉关键路径构造。
- 显式配置命中时，不调用目录判定谓词；谓词最多检查一个包内候选。
- `plugin_root(name)` 和其消费者保留现有签名，不增加多根迭代、配置上下文或文件系统 trait。

原 `plugin.rs` 已超过推荐文件大小；新增选择逻辑及单元测试放在小型私有子模块，不借本功能大规模搬迁安装器或已有测试。新模块必须与真实调用入口同一功能切片接入，不能先落无人调用的模块。

### 3.2 安装命令构造的最小测试接缝

将 `src/plugin.rs:197-219` 现有命令组装部分提取到私有 `src/plugin/install_command.rs`，保留原安装函数中的执行、二进制检查、锁读写及输出逻辑。

```rust
pub(super) fn build_install_command(
    plugin: KnownPlugin,
    root: &Path,
    path: Option<&Path>,
    force: bool,
    version: Option<&str>,
    locked: bool,
) -> Command;
```

该函数仅构造 `Command`，由现有安装入口调用，然后在原执行边界调用 `status()`。参数、顺序、`--locked` 默认值、`--path` 与 registry/version 选择均保持不变，来源元数据仍由原逻辑记录。

此提取只用于无执行地验证 cargo 的 `--root` 参数，避免测试调用真实 cargo、伪造 PATH 中的 cargo，或增加生产环境可启用的测试入口。单元测试与构造函数放在同一小文件；不注入模拟安装成功的 runner，不重构旧锁文件写入逻辑。

## 4. 消费链、数据契约与错误行为

### 4.1 保持单根一致

`plugin dir`、当前根插件的 `list`、安装、更新、删除和锁文件均进入同一个已固定的根。选中根缺少插件时，仅沿用执行器既有的 PATH 回退；不继续搜索另一个 HOME 副本，也不把 PATH 中的可执行文件纳入当前根的删除或更新目标。

`event` 对应 `sse`、`websocket` 对应 `ws` 目录下的 `netutils-websocket` 等映射保持原样（`src/plugin.rs:785-799`）。更新全部插件仍沿用现有已知插件遍历行为，不顺带改为只更新已安装项。

### 4.2 JSON 与完整性语义

不新增或重命名公开字段，不改变字段类型和顶层形状：

- `plugin dir --json` 仍为 `{"dir": "..."}`。
- `plugin list --json` 仍为既有数组，`path` 等字段只反映新选中的位置。
- 安装结果的 `root`、`binary`、`lock_path` 等字段仍使用原契约。
- 包内插件缺少锁文件时，保持既有状态及 `integrity: "unrecorded"`；不补写记录，不将自动发现描述为可信认证。
- 子进程退出码传播和输出参数转发保持不变。

### 4.3 只读与失败边界

发现、目录显示、列举及核心分派不创建目录或锁文件；已有插件自身的写入不在该保证内。

尚未选中包内目录时，主程序定位或目录判定失败可进入旧默认链。根已经选中之后，cargo、锁文件或删除遇到权限问题，不重新选择 HOME 或其他根，沿用原有错误通道。

不增加可写性预检或自动提权；这些检查既不能代替真实写操作，也会误排除只读但可使用的发行包。

保留现有“cargo 已成功、锁记录失败”的 `lock_error`/warning 行为（`src/plugin.rs:250-298`）。本功能不将安装改造成全事务回滚，也不借根目录变更悄悄改写旧错误契约。

## 5. 测试与验收设计

### 5.1 纯单元测试

路径选择单测通过输入和目录谓词覆盖：显式配置最高优先（含空、相对、不存在及平台支持的非 Unicode 值）、包内目录胜过用户目录、空目录、同名文件、定位失败或无父目录、候选不存在、USERPROFILE/HOME 优先级及原相对兜底。

用记录或断言型谓词验证检查的路径恰为主程序同级 `plugins/`，显式配置命中时不调用该谓词。单测不调用 `set_var`、`remove_var`、`set_current_dir`，不重置生产 `OnceLock`。

安装构造单测只检查 `get_program()` / `get_args()`，按 `OsStr` 验证 `--root` 后的独立参数，并覆盖空格/Unicode 路径、locked/unlocked、force、path、version。不得将参数拼成 shell 字符串，也不执行构造出的命令。

### 5.2 跨平台原生插件夹具

现有测试只会从构建目录启动核心程序，尚无真实 bundle 夹具（`tests/cli.rs:7-23`、`tests/cli_smoke.rs:13-20`）。新增夹具采用以下方式：

- 将 `CARGO_BIN_EXE_netutils` 复制到唯一临时发行目录，保持真实归档布局。
- 将当前 integration test executable 复制成各候选根中的插件二进制；这在 Windows 也是原生 `.exe`，无需 shell 脚本、实时 rustc 编译或额外 Cargo target。
- 复制后的测试程序由 libtest 参数只执行一个专用 fixture，使用完整测试名、`--exact`、`--ignored`、`--nocapture` 和单测试线程。fixture 另有子进程标记守卫，普通 `cargo test` 不触发退出分支。
- fixture 输出并 flush 自身可执行文件位置，随后使用约定退出码；借此区分实际运行的是 env、bundle、HOME 还是 PATH 中的副本。
- 子进程标记只由测试可执行文件识别，正式核心不增加测试环境变量、CLI 开关或隐藏分支。
- 实际插件运行验证不带全局 `--json`，避免把该参数传给不支持它的 libtest；JSON 的 dir/list 在独立调用中验证。

### 5.3 六组真实进程场景

| 场景 | 主要断言 | 对应需求 |
|---|---|---|
| 显式覆盖 | env/bundle/HOME 冲突时使用 env；无效显式路径不被自动目录替换；保留 PATH 兜底 | R2、R4 |
| 包内定位 | bundle 胜过 HOME；从无关 cwd、PATH 启动及整体移动后仍使用包内目录；cwd/祖先诱饵不生效 | R1、R2、R3 |
| 原方式回退 | 无包内目录或同名仅为文件时用户目录仍可用；受控 PATH-only 插件仍可执行 | R2、R3 |
| 别名与输出 | `event`、`websocket` 实际执行正确目录/二进制；dir/list 的 JSON 形状及路径一致；退出码传播 | R4、R5 |
| 无额外写入 | dir/list/run 前后插件树及隔离 HOME 的名称与内容快照一致，不生成锁文件；不比较 atime | R3、R5 |
| 管理不跨根 | 真实离线删除仅删除选中根中的插件，其他根同名副本和锁文件不变；list 读取选中根的可区分元数据 | R4、R5 |

测试为每个 `Command` 独立配置 HOME、USERPROFILE、NETUTILS_PLUGIN_DIR、cwd、语言、颜色和私有 PATH，保留 Windows 必需的系统环境。常规 PATH 指向隔离空目录；通过 PATH 启动核心的场景，只将复制的 `netutils[.exe]` 所在发行目录加入子进程 PATH；插件 PATH 回退专项只加入存放无副作用 `netutils-<fixture>` 的隔离目录。不放假 cargo、rustc 或命令解释器，不修改全局 PATH。

临时目录以 PID 和计数器产生候选，使用 `create_dir` 原子争用，碰撞重试；成功创建后立即持有清理 guard。等待核心及其等待的插件退出、关闭句柄后清理。Windows 删除临时可执行文件仅允许有上限的短重试；正常路径明确检查最终清理结果，panic 路径尽力清理而不二次 panic。

### 5.4 不夸大的覆盖声明

测试先行允许运行期或编译期 RED。若全项目依赖下载阻塞，可在仓库外的临时标准库测试 wrapper 中引用真实组件源码：先由新测试引用缺失接口取得编译期 RED，再补齐实现并运行同一组件测试取得 GREEN。命令构造组件的临时 wrapper 只提供其读取的静态插件元数据，完整父类型和 CLI 集成仍由 Cargo 回归验证。下载超时或缺少依赖本身不算产品 RED；若完整 CLI 构建直到修复后才完成，其结果只能记作修复后验证，不能冒充旧版运行期 RED。

纯选择器验证选根，纯 Command 测试验证 cargo 参数，真实子进程覆盖发现、别名、锁元数据读取和删除。旧锁写入函数仍使用同一固定根，通过调用链审阅确认没有第二套解析。

本方案不运行真实 cargo 成功安装，不把命令构造测试说成完整安装与锁落盘 E2E，也不为覆盖旧安装器增加 runner 或运行时测试后门。

三平台自动化的树快照验证“核心未写入”，不等同于真实文件系统拒写测试。真实权限验收另列：在唯一临时 bundle 内、以有效的非特权权限配置使写/删 canary 确实得到 PermissionDenied，再验证 dir/list/run 可用、删除拒写且不触碰另一根；完成后恢复临时目录权限并清理。

Windows 的目录 readonly 属性不能证明该目录不可创建文件；Unix chmod 在特权进程中也可能被绕过。因此权限夹具若未能真正拒写，必须明确记为未完成验收，不能早退成功或宣称通过。Windows 真实 ACL 验收保留为单独手工检查，不在本功能引入 ACL 自动管理框架；“未找到 cargo”也不能冒充安装权限错误。

## 7. 备选方案与取舍

| 方案 | 决定与原因 |
|---|---|
| 继续要求手工环境变量 | 拒绝：完整包已经具备所有文件，却仍不能零配置使用 |
| cwd 或任意祖先目录就近搜索 | 拒绝：启动位置改变加载对象，新增不必要的误加载面，且当前包不需要 |

| 每次调用都重新探测根 | 不采用：新增动态条件可能让同一命令前后转根；进程内固定比向全部消费者传配置对象更小 |
| 新增文件系统 trait、配置对象或目录库 | 不采用：标准库和一个可注入纯选择器已足够，无新增依赖理由 |
| 将逻辑和全部新测试继续放进 plugin.rs | 不采用：文件已过大；仅将本功能的根政策和命令构造放入私有小模块 |
| 测试注入 PATH 假 cargo、生产测试开关或安装 runner | 不采用：增加平台差异和测试后门/旧安装器模拟成本；只检查原生 Command 参数即可覆盖本次构造变化 |

## 8. 验证门与安全边界

实现阶段仍须通过仓库的三个门：

```text
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

新根选择逻辑要求稳定工具链可测的行/region 覆盖至少 80%，并用条件用例覆盖全部优先级和回退路径。所用 cargo-llvm-cov 的 `--branch` 要求 nightly，本功能不为测量擅自更换固定工具链或使用 bootstrap；不能把行/region 数值称为已测分支覆盖率。项目整体覆盖率须实际测量，不能用新增模块覆盖率冒充整体数值。现有 `--version`、命令解析和 plugin JSON 冒烟必须保留通过。权限验收与文档检查须独立记录，不以 cargo test 绿色替代。

`current_exe` 用于定位而非可信认证。其符号链接行为遵循平台语义，不额外承诺使用链接文件旁的另一个根，也不通过 argv[0] 猜测。`is_dir` 按常规文件系统语义跟随目录链接；保留原删除安全校验，不放宽 containment 检查。自动发现不提升插件权限、不认证插件来源，也不改变插件作为独立本机代码执行的信任边界。

标准库约束参考：[current_exe](https://doc.rust-lang.org/std/env/fn.current_exe.html)、[OnceLock](https://doc.rust-lang.org/1.98.1/std/sync/struct.OnceLock.html)、[模块文件规则](https://doc.rust-lang.org/reference/items/modules.html)。
